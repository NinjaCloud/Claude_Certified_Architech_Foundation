```
 8 test prompts --> Claude + tools --> which tool? which arguments?
                       ^
   flawed_tools.py ----+   (vague names, no limits, no enums)
   fixed_tools.py  ----+   (clear purpose, boundaries, enums)
                       |
      selection + typed-slot + consistency scores
```

You will learn: why tool descriptions are the main way Claude decides what to call, how to write names, boundaries, parameter descriptions and enums, and how to test a tool set instead of trusting it.

```python
"""Lab 3: measure how well Claude uses a tool set.

Usage:
    python eval_tools.py flawed_tools            # baseline
    python eval_tools.py fixed_tools --repeat 3  # your redesign

Claude is told to answer every request by calling one tool (tool_choice stays on "auto",
because newer models reject forced tool choice). If it replies in text, that counts as a miss.

Three measures:
  selection   = Claude called an acceptable tool and the key values appear in the arguments
  typed slots = each key value landed in a parameter whose NAME says what it is
                (an order ID in `order_id`, an email in `email`, a status in `status` ...)
  consistency = prompts where every repeat chose the same tool

Selection can look fine even for bad tools, because a strong model guesses well from a few
tools. Typed slots and consistency show the difference.
"""
import argparse
import importlib
import json
import os
from collections import Counter

import anthropic

MODEL = os.environ.get("CLAUDE_MODEL", "claude-sonnet-5-5")
SYSTEM = ("You are a customer-support assistant. Handle every request by calling exactly one "
          "of the available tools. Do not answer in plain text.")

# (prompt,
#  tools acceptable for the flawed set,
#  tool required for the fixed set,
#  [(value that must appear, keyword the parameter NAME must contain), ...])
TESTS = [
    ("Where is order ORD-10001 right now?",
     {"get_data", "search"}, "get_order_status", [("ORD-10001", "order")]),
    ("Show all orders from customer C-7 that are still processing.",
     {"get_data", "search"}, "list_orders", [("C-7", "customer"), ("processing", "status")]),
    ("Look up the account that belongs to maya@example.com.",
     {"fetch_user", "lookup_user"}, "find_customer_by_email", [("maya@example.com", "email")]),
    ("What phone number do we have on file for customer C-7?",
     {"fetch_user", "lookup_user", "get_data"}, "get_customer", [("C-7", "customer")]),
    ("Change the delivery address on ORD-10002 to 12 MG Road, Pune.",
     {"update"}, "update_shipping_address", [("ORD-10002", "order"), ("12 MG Road", "address")]),
    ("Has ORD-10003 shipped yet?",
     {"get_data", "search"}, "get_order_status", [("ORD-10003", "order")]),
    ("Find the customer with email raj@example.com and tell me their tier.",
     {"fetch_user", "lookup_user"}, "find_customer_by_email", [("raj@example.com", "email")]),
    ("Which of customer C-9's orders were delivered?",
     {"get_data", "search"}, "list_orders", [("C-9", "customer"), ("delivered", "status")]),
]


def pick(client, tools, prompt):
    resp = client.messages.create(model=MODEL, max_tokens=400, system=SYSTEM, tools=tools,
                                  messages=[{"role": "user", "content": prompt}])
    call = next((b for b in resp.content if b.type == "tool_use"), None)
    if call is None:                       # Claude answered in text: no tool chosen
        return "(no tool)", {}
    return call.name, call.input


def in_typed_slot(args, value, keyword):
    """True if `value` sits inside a parameter whose name contains `keyword`."""
    return any(keyword in key.lower() and value.lower() in str(val).lower()
               for key, val in args.items())


def main(module_name, repeat, client=None):
    tools = importlib.import_module(module_name).TOOLS
    client = client or anthropic.Anthropic()
    flawed = module_name.startswith("flawed")
    n = sel = fit = consistent = 0
    for prompt, flawed_ok, fixed_ok, slots in TESTS:
        acceptable = flawed_ok if flawed else {fixed_ok}
        picks = [pick(client, tools, prompt) for _ in range(repeat)]
        names = [name for name, _ in picks]
        sel_hits = [name in acceptable and all(v.lower() in json.dumps(a).lower() for v, _ in slots)
                    for name, a in picks]
        fit_hits = [all(in_typed_slot(a, v, k) for v, k in slots) for _, a in picks]
        same = len(set(names)) == 1
        n += repeat
        sel += sum(sel_hits)
        fit += sum(fit_hits)
        consistent += same
        print(f"selection: {'ok  ' if all(sel_hits) else 'MISS'}  typed slots: {'ok  ' if all(fit_hits) else 'MISS'}"
              f"  consistent: {'yes' if same else 'NO '}  | {prompt}")
        print(f"      picks: {dict(Counter(names))}")
        print(f"      example call: {picks[0][0]}({json.dumps(picks[0][1])})")
        if not all(fit_hits):
            missing = [f"{v!r} in a '*{k}*' parameter" for v, k in slots if not in_typed_slot(picks[0][1], v, k)]
            if missing:
                print(f"      no typed slot for: {', '.join(missing)}")
    print(f"\n{module_name}: selection {sel}/{n}, typed slots {fit}/{n}, consistent prompts {consistent}/{len(TESTS)}")


if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("module", nargs="?", default="flawed_tools")
    ap.add_argument("--repeat", type=int, default=3)
    a = ap.parse_args()
    main(a.module, a.repeat)
```

*Why:*
- Each test is a user request plus the tool a good design should pick and the key values (an order ID, an email) that must appear in the arguments.
- The system prompt tells Claude to handle every request by calling one tool. `tool_choice` stays on its default (`auto`), because newer models such as Sonnet 5.5 reject forced tool choice. If Claude answers in text instead of calling a tool, the eval records `(no tool)` and counts it as a miss. That is also a useful signal: the tools were unclear.
- Every prompt runs `--repeat` times (default 3). Three measures are reported:
  - **Selection:** Claude called an acceptable tool and the key values (order ID, email, status) appear somewhere in the arguments. For the flawed set, any reasonable-looking tool is accepted, so this measure is generous. For the fixed set, only the one right tool counts.
  - **Typed slots:** each key value landed in a parameter whose **name says what it is**: an order ID in `order_id`, an email in `email`, a status in `status`. A value stuffed into `id`, `name` or `query` does not count.
  - **Consistency:** all repeats of a prompt chose the same tool.

Expected output (your picks may differ, but the pattern should look like this):

```
selection: ok    typed slots: MISS  consistent: yes  | Where is order ORD-10001 right now?
      picks: {'get_data': 3}
      example call: get_data({"id": "ORD-10001"})
      no typed slot for: 'ORD-10001' in a '*order*' parameter
selection: ok    typed slots: MISS  consistent: yes  | Look up the account that belongs to maya@example.com.
      picks: {'lookup_user': 3}
      example call: lookup_user({"name": "maya@example.com"})
      no typed slot for: 'maya@example.com' in a '*email*' parameter
...
flawed_tools: selection 24/24, typed slots 0/24, consistent prompts 8/8
```

*Why, read it honestly:* **selection looks perfect.** A strong model is good at guessing the right tool from only five, so do not expect failures there. The weakness is in the **arguments**. Look at the example calls: an order ID goes into `id`, an email goes into a parameter called `name`, and the customer and status filter are squeezed into one free-text `query`. Claude guessed correctly, but nothing in the tool definitions told it, and the server cannot validate anything because every slot is an untyped string. Change the model, the wording, or add more tools, and the guesses start to break. In a real system with 30 to 50 overlapping tools this also becomes inconsistent tool choice. Typed slots is the measure that shows the design problem even when the model is coping.

### 5. Write your redesign

Create `fixed_tools.py` with a list named `TOOLS`. It must contain exactly these five tools, so the eval can score them:

| Tool name | Purpose | Parameters |
|---|---|---|
| `get_customer` | Profile of one customer by ID | `customer_id` (string, like C-7) |
| `find_customer_by_email` | Find one customer by exact email | `email` (string) |
| `get_order_status` | Status, carrier, ETA of one order | `order_id` (string, like ORD-10001) |
| `list_orders` | Orders of one customer, optional status filter | `customer_id` (required), `status` (optional enum: processing, shipped, delivered, cancelled) |
| `update_shipping_address` | Change address of one unshipped order (write) | `order_id`, `new_address` (both required) |

Use the design rules below for every tool:

1. **Name = verb + object.** The name alone should say what it does.
2. **Description = what it returns, when to use it, when not to.** Mention the boundary with the closest neighbour tool.
3. **One description per parameter**, with an example value.
4. **Enums** for fixed sets of values.
5. **Mark writes** clearly (for example "Writes data").

Here is a finished example to copy the pattern from:

```python
def _tool(name, description, props, required):
    return {"name": name, "description": description,
            "input_schema": {"type": "object", "properties": props, "required": required}}

          "Get the current status, carrier and ETA of ONE order by order ID (like ORD-10001). "
          "Use for 'where is my order' or 'has it shipped'. Do not use to list orders or change them.",
          {"order_id": {"type": "string", "description": "Order ID such as ORD-10001"}}, ["order_id"]),
```

### 8. Design error responses (paper exercise, 5 minutes)

For `get_order_status`, write down what the tool should return when the order does not exist. A good answer is structured, not a plain string:

```json
{"is_error": true, "error_category": "not_found", "retryable": false,
 "message": "No order ORD-99999", "hint": "Ask the customer to confirm the ID"}
```

*Why:* the model needs to know whether to retry, ask the user, or give up. Lab 4 returns exactly this shape from a real server.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `400 ... tool_choice: type "tool" and "any" are not supported for this model` | You are running an older copy of `eval_tools.py` that forces a tool. Use the version in this lab: it has no `tool_choice` argument. |
| `ModuleNotFoundError: fixed_tools` | The file must be named `fixed_tools.py` and sit in `C:\cca-labs\lab03`. |
| `selection: MISS` with the correct tool | The key value is missing from the arguments. Make sure the parameter descriptions tell Claude to pass the full value (full email, full address). |
| `typed slots: MISS` on your fixed tools | A parameter name does not contain the expected word. Use `order_id`, `customer_id`, `email`, `status`, `new_address` as in the table. |
| Baseline selection is 24/24 and consistency 8/8 | Normal. A strong model guesses well from five tools. The weakness shows in typed slots, and in the example calls. Discuss how a 40-tool set would behave. |
| `400 invalid_request_error: tools.0.custom.input_schema` | Your schema is not valid JSON Schema. Each tool needs `"type": "object"` and a `properties` dict. |

## Exam takeaways

- The **description is the interface**: purpose, limits, and when not to use it.
- Fewer, clearer, well-separated tools beat many overlapping ones.
- Use **enums and parameter descriptions** to constrain arguments.
- Return **structured errors** (category, retryable, hint).
- **Evaluate** tool selection with realistic prompts; do not assume.
