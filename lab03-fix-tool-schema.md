## What you will build

A small **tool-selection eval** and a redesigned tool set. You measure how reliably Claude chooses the right tool from five badly designed tools, rewrite them, and measure again.

```
 8 test prompts --> Claude + tools --> which tool? which arguments?
                       ^
   flawed_tools.py ----+   (vague names, no limits, no enums)
   fixed_tools.py  ----+   (clear purpose, boundaries, enums)
                       |
                 accuracy + consistency score
```

You will learn: why tool descriptions are the main way Claude decides what to call, how to write names, boundaries, parameter descriptions and enums, and how to test a tool set instead of trusting it.

```python
"""Lab 3: measure how reliably Claude picks the right tool.

Usage:
    python eval_tools.py flawed_tools            # baseline
    python eval_tools.py fixed_tools --repeat 3  # your redesign

tool_choice={"type": "any"} forces a tool call, so we see exactly which tool Claude picks.
Each prompt runs --repeat times. Two numbers matter:
  accuracy    = picks that used an acceptable tool AND passed the key value in the arguments
  consistency = prompts where every repeat picked the same tool
"""
import argparse
import importlib
import json
import os
from collections import Counter

import anthropic

MODEL = os.environ.get("CLAUDE_MODEL", "claude-sonnet-5-5")

# (prompt, tools acceptable for the flawed set, tool required for the fixed set, strings that must appear in the arguments)
TESTS = [
    ("Where is order ORD-10001 right now?", {"get_data", "search"}, "get_order_status", ["ORD-10001"]),
    ("Show all orders from customer C-7 that are still processing.", {"get_data", "search"}, "list_orders", ["C-7", "processing"]),
    ("Look up the account that belongs to maya@example.com.", {"fetch_user", "lookup_user"}, "find_customer_by_email", ["maya@example.com"]),
    ("What phone number do we have on file for customer C-7?", {"fetch_user", "lookup_user", "get_data"}, "get_customer", ["C-7"]),
    ("Change the delivery address on ORD-10002 to 12 MG Road, Pune.", {"update"}, "update_shipping_address", ["ORD-10002", "12 MG Road"]),
    ("Has ORD-10003 shipped yet?", {"get_data", "search"}, "get_order_status", ["ORD-10003"]),
    ("Find the customer with email raj@example.com and tell me their tier.", {"fetch_user", "lookup_user"}, "find_customer_by_email", ["raj@example.com"]),
    ("Which of customer C-9's orders were delivered?", {"get_data", "search"}, "list_orders", ["C-9", "delivered"]),
]


def pick(client, tools, prompt):
    resp = client.messages.create(model=MODEL, max_tokens=300, tools=tools,
                                  tool_choice={"type": "any"},
                                  messages=[{"role": "user", "content": prompt}])
    call = next(b for b in resp.content if b.type == "tool_use")
    return call.name, call.input


def main(module_name, repeat, client=None):
    tools = importlib.import_module(module_name).TOOLS
    client = client or anthropic.Anthropic()
    flawed = module_name.startswith("flawed")
    good = right = consistent = 0
    for prompt, flawed_ok, fixed_ok, must in TESTS:
        acceptable = flawed_ok if flawed else {fixed_ok}
        picks = [pick(client, tools, prompt) for _ in range(repeat)]
        names = [n for n, _ in picks]
        hits = [n in acceptable and all(m.lower() in json.dumps(a).lower() for m in must) for n, a in picks]
        good += sum(hits)
        right += len(hits)
        same = len(set(names)) == 1
        consistent += same
        print(f"{'PASS' if all(hits) else 'FAIL'}  {prompt}")
        print(f"      picks: {dict(Counter(names))}   consistent: {same}")
        print(f"      example call: {picks[0][0]}({json.dumps(picks[0][1])})")
    print(f"\n{module_name}: accuracy {good}/{right}, consistent prompts {consistent}/{len(TESTS)}")


if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("module", nargs="?", default="flawed_tools")
    ap.add_argument("--repeat", type=int, default=3)
    a = ap.parse_args()
    main(a.module, a.repeat)
```

*Why:*
- Each test is a user request plus the tool a good design should pick and the key values (an order ID, an email) that must appear in the arguments.
- `tool_choice={"type": "any"}` forces Claude to call some tool, so you see its choice instead of a chat answer.
- Every prompt runs `--repeat` times (default 3). **Accuracy** counts correct tool plus correct arguments. **Consistency** counts prompts where all repeats chose the same tool.
- For the flawed set, any reasonable-looking tool is accepted, so the baseline is generous. For the fixed set, only the one right tool counts.

### 5. Write your redesign

Create `fixed_tools.py` with a list named `TOOLS`. It must contain exactly these five tools, so the eval can score them:

| Tool name | Purpose | Parameters |
|---|---|---|
| `get_customer` | Profile of one customer by ID | `customer_id` (string, like C-7) |
| `find_customer_by_email` | Find one customer by exact email | `email` (string) |
| `get_order_status` | Status, carrier, ETA of one order | `order_id` (string, like ORD-10001) |
| `list_orders` | Orders of one customer, optional status filter | `customer_id` (required), `status` (optional enum: processing, shipped, delivered, cancelled) |
| `update_shipping_address` | Change address of one unshipped order (write) | `order_id`, `new_address` (both required) |

Use the design rules below for every tool:

1. **Name = verb + object.** The name alone should say what it does.
2. **Description = what it returns, when to use it, when not to.** Mention the boundary with the closest neighbour tool.
3. **One description per parameter**, with an example value.
4. **Enums** for fixed sets of values.
5. **Mark writes** clearly (for example "Writes data").

Here is a finished example to copy the pattern from:

```python
def _tool(name, description, props, required):
    return {"name": name, "description": description,
            "input_schema": {"type": "object", "properties": props, "required": required}}

TOOLS = [
    _tool("get_order_status",
          "Get the current status, carrier and ETA of ONE order by order ID (like ORD-10001). "
          "Use for 'where is my order' or 'has it shipped'. Do not use to list orders or change them.",
          {"order_id": {"type": "string", "description": "Order ID such as ORD-10001"}}, ["order_id"]),
    # TODO: add the other four tools
]
```

### 8. Design error responses (paper exercise, 5 minutes)

For `get_order_status`, write down what the tool should return when the order does not exist. A good answer is structured, not a plain string:

```json
{"is_error": true, "error_category": "not_found", "retryable": false,
 "message": "No order ORD-99999", "hint": "Ask the customer to confirm the ID"}
```

*Why:* the model needs to know whether to retry, ask the user, or give up. Lab 4 returns exactly this shape from a real server.

| Eval prints `FAIL` with correct tool | The argument check failed. Make sure the parameter descriptions tell Claude to pass the full value (full email, full address). |

## Exam takeaways

- The **description is the interface**: purpose, limits, and when not to use it.
- Fewer, clearer, well-separated tools beat many overlapping ones.
- Use **enums and parameter descriptions** to constrain arguments.
- Return **structured errors** (category, retryable, hint).
- **Evaluate** tool selection with realistic prompts; do not assume.
